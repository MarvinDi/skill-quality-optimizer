## 坑一：description 缺少触发条件

### 问题
`description` 只写“我会干什么”，没写“什么时候找我”。AI 启动时只装载 `name`+`description`，如果 description 不包含触发场景，AI 无法在合适时机调用该技能。

### 检查方法
只看 `description`，找一个不了解这个项目的人读一遍，问他觉得什么时候该用。答不上来就重写。

### 修复示例

**❌ 改前**：
```
description: "从 PDF 财报里提取营收、净利润、同比增长率，输出 JSON。"
```

**✅ 改后**：
```
description: "从 PDF 季度财报里提取营收、净利润、同比增长率，输出 JSON。用户提到‘财报’‘季报’‘提取财务数据’时使用。"
```

### 验证标准
description 必须同时包含：
1. 技能做什么（功能）
2. 什么情况下调用（触发条件/关键词/场景）

## 坑二：一技多事，未拆分

### 问题
一份技能干三件事（甚至四件），AI 每次都要在几千行里找此刻需要的几十行。正文越长，分给当前任务的注意力越薄。

### 检查方法
数行数。超过 500 行，先想怎么拆。

### 修复方法
拆分为三层结构：

```
SKILL.md          <- 概览 + 导航（<500行）
references/       <- 细节文件，用到才读
  ├── 文件A.md    <- 单个文件>100行时，顶部加目录
  ├── 文件B.md    <- 文件名能看出内容，避免 doc1.md/doc2.md
  └── 文件C.md
```

### 配套规则
1. 引用只能一层：SKILL.md 只能直接引用 `references/` 下的文件，不能再嵌套引用。
2. 单个参考文件超过 100 行，顶部加目录。
3. 文件名要能看出内容，避免 `doc1.md`、`doc2.md`。

## 坑三：只写要求，不写样例

### 问题
正文只写要求，没有代码块输出示例。AI 看到例子会照抄字段名、粒度、缩进，示例的作用是定标，不是说明。

### 检查方法
翻一遍正文，看有没有代码块。一个都没有，就要加一段最简单的输出示例。

### 修复示例

在 SKILL.md 结尾添加：

```markdown
## 输出示例

```json
{
  "revenue": 1000000,
  "net_profit": 200000,
  "growth_rate": 0.15
}
```
```

### 验证标准
正文中至少包含一个代码块，展示该技能的典型输出格式。

## 坑四：多处规则重复

### 问题
同一件事在技能、项目规则文件、系统提示里各写了一遍。漏删的那份平时不出声，等改了留下的那一处才开始起作用，容易造成冲突。

### 检查方法
把技能、项目规则、系统提示摊在一起，看有没有对同一件事说了两种话。

### 修复方法
1. 先定义归谁管（哪个文件是权威来源）。
2. 从别处删掉重复定义。
3. 保留一处真理来源，其他地方引用或删除。

## 坑五：未多 phrasing 测试

### 问题
写完就发，没跑过。同一个需求换三种说法，AI 可能走到不同路径，说明有条规则被绕过去，或两处规则在打架。

### 检查方法
同一个需求，换三种说法各跑一遍，看 AI 是否都走到同一条路上。

参见 `test-phrasings.md`。

## 快速自查清单

1. [ ] 只看 description，不熟悉项目的人能说出什么时候该用吗？
2. [ ] 行数 < 500？超过则拆分。
3. [ ] 正文至少有一个代码块输出示例？
4. [ ] 技能、项目规则、系统提示中，同一事只定义一次？
5. [ ] 同一个需求换三种说法测试，都触发同一条路径？
